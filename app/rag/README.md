# RAG Pipeline

Semantic search and retrieval-augmented answers over your own CVs, interview feedback,
and company research — grounded in documents you've actually saved, not general
knowledge.

## How it works

This section walks through the whole journey of a document, from the moment you upload
it to the moment it's used to answer a question.

### Stage 1: You upload a document

You save a CV, a set of interview notes, or a company research note through the app
(API or the MCP)  `add_document` tool. The raw text is saved immediately, as-is, in the `documents` table.

### Stage 2: A background job gets queued to prepare it for search

Saving a document also asks a background worker (Celery) to come along later and
process it for search. This happens in the background on purpose: turning a document
into something searchable takes a moment and it has to call an external AI service.

### Stage 3: Chunking the document

A whole CV or a long research note is too big and too mixed-topic to search well as
one block. So the document is cut into smaller pieces, called chunks, roughly a short paragraph or 
two each.

This cutting isn't arbitrary. It tries to respect the document's natural shape by:
- Cutting on blank lines (paragraph breaks), not mid-sentence.
- Trying to identify section header (e.g. "EXPERIENCE", "Education"). It keeps it glued to the paragraph that follows it, so you never end up with a chunk that's just a lonely heading and no content.
- Keeping a little bit of the previous chunk's ending stacked onto its start. That way, if an important sentence happens to sit right on the boundary between two chunks, it isn't cut off and lost.

### Stage 4: Embedding

Each chunk of text is sent to an AI embedding model (OpenAI's`text-embedding-3-small`), which converts it into a list 
of 1,536 numbers called vector. It's generated by LLM "fingerprint" with meaning of a chunk. Two chunks that say 
similar things in different words end up with similar looking fingerprints.

### Stage 5: Storing chunks and their fingerprints

Each chunk, its embedding fingerprint, and a plain-text copy for keyword matching are
saved to a `document_chunks` table, that has relation to the original document. From this
point on, the document is fully searchable by "meaning" via the fingerprints,
and by exact words via a normal keyword search.

### Stage 6: Asking a questions and running the search

This is the "Retrieval" half of RAG. When you search or ask a question, two searches
run side by side over the stored chunks:

1. Meaning search. Each question is turned into its own fingerprint (the same way
   chunks were), and the system finds chunks whose fingerprints look most similar. This
   catches chunks that mean the same thing as your question even if they're phrased
   completely differently.
2. Keyword search. Traditional search for the exact words in the question. This
   catches specific names, tools, or acronyms that a meaning-based search might skip.

Neither search alone is reliable enough on its own, so both run every time and their
results are combined into one, merged ranking. The best ranked chunks are the ones carried forward.
If agent was asked for search, RAG pipeline ends up at this stage.

### Stage 7: Generation

It there was a question asked or analysis required, the top chunks are handed to Agent as reference material, 
along with an instruction: "answer using only what's in these excerpts, and say which excerpts you used." Agent
then writes an answer and marks which numbered excerpt backs up each part of it.

## Chunking

`app/rag/chunking.py` splits on blank-line boundaries into paragraphs, merges any
short header-like line (all-caps, Title Case, or markdown `#`) into the paragraph that
follows it so section headers never end up alone in their own chunk, then greedily
packs paragraphs into ~400-token chunks with a ~60-token overlap carried across every
chunk boundary. A single long paragraph with no natural breaks (a long free-form note)
is split with a sliding word-boundary window instead of packed whole. This is
deliberately simple and dependency-free (no NLP library, no tokenizer — a fixed
chars-per-token heuristic is used only for sizing), and it works for both kinds of
content this app stores: structured CV sections (headers stay attached to their body)
and free-form notes (plain paragraph packing with overlap).

## Embeddings

The embedding provider is pluggable behind `EmbeddingProvider` (`app/rag/embeddings.py`)
— one `embed_texts(texts) -> vectors` method. The default implementation is OpenAI's
**`text-embedding-3-small`**: 1536 dimensions, which matches the `EMBEDDING_DIM` already
used by the pgvector column (no schema change needed to adopt it), cheap
($0.02/1M tokens), and a simple, well-documented SDK. Swapping providers (e.g. to
Voyage AI, Anthropic's recommended embeddings partner — Anthropic doesn't offer a
first-party embeddings API) means implementing `EmbeddingProvider` and changing
`get_embedding_provider()`; nothing else in the codebase depends on OpenAI directly.

Chunk embeddings live in a new `document_chunks` table (one row per chunk, its own
`Vector(1536)` column, FK to `documents`) rather than the single `embedding` column on
`Document` — retrieval needs one vector per chunk, not one per whole document, so
`Document.embedding` is left in place but is no longer used by the RAG pipeline.

## Hybrid retrieval

`app/services/retrieval_service.py` runs two independent searches and merges them:

- **pgvector cosine similarity** over chunk embeddings — catches paraphrases and
  semantically related passages that share no vocabulary with the query, but can miss
  an exact keyword, name, or acronym that carries little semantic weight.
- **Postgres full-text search** (`tsvector`/`websearch_to_tsquery`/`ts_rank`) — the
  mirror image: excellent at exact terms, blind to paraphrase.

Recalibrating and combining their two incompatible raw score scales is unnecessary —
instead the two ranked lists are merged with **Reciprocal Rank Fusion** (`RRF_K = 60`,
the constant from Cormack, Clarke & Buettcher's 2009 RRF paper): each chunk's score is
the sum of `1 / (RRF_K + rank)` over every list it appears in, using only rank
position. A chunk that ranks well on both signals reliably outranks one that ranks well
on only one.

No ANN index (ivfflat/hnsw) is built on `document_chunks.embedding` — at a personal
corpus's scale (low hundreds of chunks) a brute-force cosine scan is effectively
instant, and ANN indexes need a representative data distribution to tune (`lists`/
`probes`) that doesn't exist yet. Worth revisiting if the corpus grows substantially.

## Generation

`app/services/answer_service.py` takes retrieved chunks, builds a numbered context
block, and asks Claude (`claude-opus-4-8`, adaptive thinking, `effort: "medium"`) to
answer using only that context, citing excerpts by number. `match_job_to_profile(job_id)`
is the same idea specialized to job fit: it retrieves the CV/experience chunks most
relevant to a job's title/company/description and asks for a structured fit analysis
(matching qualifications, gaps, overall recommendation). Both return an answer plus a
list of citations back to the source documents (id, title, type, chunk id).

## Running ingestion locally

Ingestion runs as a Celery task, so a broker and a worker are needed for documents to
actually get chunked and embedded (search/ask endpoints work fine without one — they
just won't find anything until ingestion has run):

```bash
# Redis, however you prefer to run it, e.g.:
docker run --rm -p 6379:6379 redis:7-alpine

# in another terminal:
uv run celery -A app.celery_app worker --loglevel=info
```

Set `OPENAI_API_KEY` in `app/config/.env` (see `.env.example`).
If the broker isn't reachable, saving a document still succeeds — ingestion is queued
best-effort and simply doesn't run until a worker/broker is available.
